# UR团队的交付纪律

这是团队预设/任务的使用纪律，不是Subagentbook对特定审查方法的内置调度。权限由运行时执行，Persona和模型自述不能扩大权限。

## 交付裁决与复核范围

2026-11-02 团队候选根据 R18–R20 实战调整，效果待新任务验证。每条发现应区分事实、证据、实际影响和是否阻断交付。C/W/S 不自动替代交付决定：阻断须明确违反哪项验收条件、影响何种功能/安全/数据，或为何会导致错误验收与后续操作。文档事实错误仍需订正；不因局部历史措辞或登记精度的偏差自动扩大为整项产品阻断，也不静默降低真实风险。

根负责在授权范围内结合独立意见裁决，交付结果为已验证交付、带非阻断遗留交付或真实阻断；只有产品取舍/权限确需用户决定时才回交用户。修复后的版本必须经独立复核，但可按差异聚焦修复与影响面；测试复用须说明输入与环境依据并明确未重跑，代码或相关环境变化则补对应测试。当前状态用权威落点加引用，不为审查报告新增更多重复计数和未经验证的历史因果说明。

插件验收另记派遣树、权限边界、分页报告完整性、恢复和终态；项目结论不能代替这些检查，模型报错也不能直接当作插件缺陷。示例调整不会更新已冻结实例，验证新 Persona 必须创建新根和新子级。

- 根执行者实现后实际委派跑者；跑者直接调用独立验证副本角色，主审及各视角按需要只读取证。独立副本已由宿主创建，核验者使用自己的cwd、重建本轮产物，修复后再创建新的核验实例。
- 若结果含非空 `report.nextOffset`，先用 `subagentbook_result` 读完全部页，再带角色/实例/轮次归属保存原文。预览不是完整报告，不应把截断处以自己的转述补成“独立原文”。
- 保存one-shot完整原文优先使用[确定性报告导出](report-export.md)，GUI下载或本地CLI直接读取宿主结果；模型分页读取用于理解，不再承担逐字复制落盘。轮次索引记录实例/父级ID、来源角色和正文SHA，解释与统计另存。
- 每条发现使用稳定ID；可拆分的子项使用例如 `F07.1/F07.2`。整条发现数与子项处置数分别统计；一条部分修复、部分延后时，不重复算成两条新发现。完整结论说明C/W/S归类、修复与反证、未验证边界。
- 每轮构建/测试保留命令、cwd、退出结果、原始日志及XML/TRX清单。在过滤复跑或下一轮会覆盖报告目录之前，复制本轮报告到独立证据目录并保存哈希。构建缓存、来源指纹、旧DLL和会话completed均不能代替真实测试证据。
- 主审与核验者返回原文由跑者带归属落盘；后续验收者的修订/恢复件另存，保留模型原始输出。修复后重审，并在约定的退出条件满足时如实收尾。

## 跑者失败时的只读入口

[可选团队示例](../examples/ur-team.json)沿用22号实战的九角色，另加 `review-relay`。根角色 `developer` 可以委派 `runner`、`review-relay` 或 `focused-review`。中继的 `actionScope` 是运行时 `read-only`，只允许委派 `chief`、`expert`、`docs`；主审再委派三个视角。`developer(0) → review-relay(1) → chief(2) → perspective(3)` 沿用原生根深度3。

仅新增或收紧防御性测试断言时，开发者或跑者运行相关测试后，默认交给一名 `focused-review` 审查最终差异、测试数据和运行证据。该角色只读，无委派边，嵌套深度为零。

跑者失败后，根停止该轮收口声称，保留原失败记录，创建新的只读中继任务。任务明确审查范围、当前版本与原报告索引；中继收集独立结论，修复由根执行者做。不得改用可写runner并仅在提示词中要求只读，也不得临时扩大既有实例的委派白名单。核验副本仍由可写runner直接创建，中继不能借核验角色扩权。

示例不自动装入任何实例。角色Persona复用22号团队保存的模型自写候选，中继复用chief Persona；路由为当时的MiMo Pro，属于候选组合。没有携带私有思考档位ID或固定输出预算；使用前通过GUI按当前供应商/模型配置思考与预算，核对权限和工具。既有实例继续使用原快照；新增降级入口需要在新根任务生效，不能假定给配置加边会赋予旧根新权限。

## 最终版本必须对应实际审查

为每轮创建新的不可覆盖检查点和独立报告目录，在项目目录外或Git忽略的证据目录存放。命令在Subagentbook仓库执行：

```bash
npm run review:checkpoint -- freeze '/absolute/project' '/absolute/evidence/r04-input.json'
npm run review:checkpoint -- check '/absolute/project' '/absolute/evidence/r04-input.json'
```

1. 完成当前批代码、测试及受影响说明的编辑，再freeze；把返回的revision和检查点路径提供给独立审查方。
2. 审查方确认对应revision、实际只读权限、当前任务范围，交付自己的原始报告及稳定发现ID。报告需引用该revision；执行结束、拒绝文本和预批条件都不能代替审查结论。
3. 审查结束和最终交付前分别运行check。退出0仅证明输入未漂移；退出1表明漂移，必须重新冻结并独立复审。退出2是参数/读取错误，也不能放行。
4. 修复任何发现（包括最后一条W或顺手修的S）都产生新版本。保存旧审查原文，不把“修完可通过”写成修改后已经通过；新轮必须明确核实修复与影响面。
5. 收口列出最终revision、独立审查实例/只读权限、完整报告哈希、未解决项与测试原始证据。不能仅凭检查点一致就宣称C/W清零。

检查点覆盖HEAD、跟踪文件（包括删除状态）、非忽略的未跟踪文件、内容和文件模式。忽略的依赖/缓存/证据不计入；外部供应商配置、环境和工具链需另记，不在此指纹内。符号链接/特殊文件/子模块等当前拒绝，不能把失败绕过为通过。此工具用于人工或脚本对账，不是模型报告真实性或语义完成度的自动裁判，也不会拦截模型在自由文本中作出错误声称。
